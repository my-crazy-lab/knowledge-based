# WiredTiger

- Document-level Locking
- Cho phép nhiều luồng đọc và ghi đồng thời vào các tài liệu khác nhau trong cùng một collection.
- Không bị khóa toàn bộ collection như MMAPv1 → tăng hiệu trong môi trường nhiều người dùng.
- Khái niệm Journaling (Ghi trước)
    - Journaling là một kỹ thuật dùng để đảm bảo tính toàn vẹn và bền vững dữ liệu trong trường hợp hệ thống bị sập đột ngột (như mất điện, lỗi hệ điều hành, hoặc crash phần cứng).
    - MongoDB sử dụng một file journal để ghi lại tất cả các thay đổi dữ liệu (insert, update, delete) trước khi thực hiện ghi vào file dữ liệu chính.
- Mỗi 60 giây (mặc định), WiredTiger sẽ thực hiện một checkpoint để ghi tất cả những thay đổi từ journal vào dữ liệu thực tế (các file dữ liệu của MongoDB).
- Điều này giúp giảm bớt thời gian khôi phục sau sự cố, vì MongoDB chỉ cần phải đọc các journal log kể từ checkpoint gần nhất thay vì quét toàn bộ dữ liệu.
- Dữ liệu "nóng" trong bộ nhớ:
    - Dữ liệu thường xuyên truy cập (dữ liệu "nóng") sẽ được giữ trong bộ nhớ để giảm độ trễ.
    - MongoDB quyết định nên giữ gìn dữ liệu nào trong bộ nhớ và đẩy dữ liệu ít truy cập ra ngoài bộ nhớ.
- Bộ nhớ đệm (Cache) trong WiredTiger:
    - Mặc định, WiredTiger sử dụng 50% bộ nhớ RAM của hệ thống cho bộ nhớ đệm (cache).
    - Bộ nhớ đệm này chứa dữ liệu và chỉ mục cần thiết cho các truy vấn và thao tác ghi.
- Khi bộ nhớ đệm đầy, WiredTiger sẽ đẩy dữ liệu cũ ra để nhường chỗ cho dữ liệu mới. Đây là quá trình eviction, giúp hệ thống hoạt động hiệu quả hơn.
    - Nếu hệ thống có ít bộ nhớ, quá trình eviction sẽ xảy ra nhiều hơn, và MongoDB có thể phải truy xuất dữ liệu từ đĩa thay vì từ bộ nhớ.
- WiredTiger hỗ trợ các thuật toán nén phổ biến sau đây:
    - Snappy: Thuật toán nén nhẹ, nhanh nhưng không nén mạnh mẽ như các thuật toán khác. Thích hợp cho các ứng dụng cần tốc độ nhanh mà không cần phải nén dữ liệu quá nhiều.
    - zlib: Thuật toán nén mạnh mẽ, sử dụng nhiều tài nguyên hơn và tốn thời gian hơn Snappy, nhưng nén dữ liệu rất hiệu quả.
    - zstd: Thuật toán nén mới hơn, cung cấp sự cân bằng giữa tốc độ và tỷ lệ nén. Nó có thể mang lại tốc độ nén nhanh và tỷ lệ nén cao. 

#  How does MongoDB detect client disconnection and terminate the query in progress?

- MongoDB has an operation context (OpContext) for every query. When the connection drops, this context is canceled, and the server will:
    - Interrupt running queries (killOp)
    - Roll back uncommitted transactions (if any)
    - Free up resources

# If you close the connection while the query is running

- The query is aborted on the server side.
- MongoDB detects the client disconnection and terminates the query in progress.
- Any partially returned data is lost — nothing will be returned to the client.
- On the client side, you'll typically get a network or timeout error depending on how you handle the close.

# Anatomy the mongo pipeline

- The aggregation pipeline is a framework for transforming documents in stages

## Cursor-Driven Pipeline Execution: Deep Dive

- Cursors as Lazy Iterators
    - When you run an aggregation, MongoDB returns a cursor, which behaves like a lazy iterator:
    - It doesn't load all documents at once.
    - It processes and returns batches of documents as needed (default batch size is 101 for the shell).
    - This allows MongoDB to handle large data sets without blowing up memory. 
- Pipeline Pull Model (not push): `[ Stage A ] → [ Stage B ] → [ Stage C ]`. How it processes:
    - Stage C asks Stage B for one document.
    - Stage B asks Stage A for one document.
    - Stage A pulls from the cursor from the collection.
    - The document flows upstream stage by stage — A → B → C.
    - Once Stage C has one result, it yields it to the client.
    - Then it repeats.
